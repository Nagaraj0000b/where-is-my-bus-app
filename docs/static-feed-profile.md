# Static feed profile — `delhi_buses_static_gtfs_v1`

Phase 1 reconnaissance. What the Delhi static GTFS actually contains, measured
rather than assumed. Feed version **v28**, declared valid 2025-01-01 → 2040-01-01.

Reproduce with `node tools/profile-gtfs.js <dir>`. Re-run it on every new
snapshot — the diff between two runs is the measurement of how stale Delhi's
static data goes.

## Size

| file | rows |
|---|---|
| `agency.txt` | 2 (DTC, DIMTS) |
| `calendar.txt` | 1 |
| `stops.txt` | 6,872 |
| `routes.txt` | 2,648 |
| `trips.txt` | 121,844 |
| `shapes.txt` | 770,824 points / 2,648 shapes |
| `stop_times.txt` | 3,855,149 |

Encoding is clean UTF-8, LF endings, no BOM. `stops.txt` uses quoted fields.

## Structure

**Referential integrity is perfect.** Zero orphans: every `trip_id`, `stop_id`,
`route_id` and `shape_id` resolves. Real foreign keys hold, which is why the
schema uses them.

**Route ↔ shape is strictly 1:1.** No route has two shapes; no shape is shared
by two routes. A "route" in this feed is therefore already a *directed* path.

**Direction lives in the route name, not `direction_id`.** 1,292 names end in
`UP`, 1,270 in `DOWN`, 86 in neither. `routes.direction_tag` captures this at
load time so queries don't re-parse strings.

**`trip_id` = `route_id` + `_HH_MM`** on all 121,844 rows. Trips are pure
timetable expansions of a route — 33 per route at the median, up to 230.

**`route_long_name` == `route_short_name`** on all 2,648 rows. The readable
"A to B" text is in `route_desc`.

## What is missing or fake

1. **There is no calendar.** One `service_id`, all seven days, 2025-01-01 to
   2040-01-01. Every trip nominally runs every day for fifteen years.
2. **`direction_id`, `block_id`, `trip_headsign`, `trip_short_name` are empty
   on every row.** No `block_id` means static data cannot tell you which trip a
   vehicle performs next — that has to come from the realtime archive.
3. **`arrival_time` == `departure_time` on 100% of rows.** No dwell time is
   modelled anywhere.
4. **`stop_dist` is blank on all 3,855,149 rows.** The feed defines the column
   and never populates it. This is the single most costly gap: it would have
   given each stop's distance along its route directly.

## What is better than expected

**`shape_dist_traveled` is fully populated** — 0 blanks across 770,824 points —
**and it is genuinely in metres.** Comparing the feed's declared route length
against PostGIS's WGS84 spheroid measurement:

| ratio min | median | max | shapes off by >2% |
|---|---|---|---|
| 0.999 | 1.002 | 1.004 | 0 of 2,648 |

So the linear reference the feed ships can be trusted as-is. That is the raw
material for computing the stop offsets `stop_dist` should have contained.

Route lengths: p05 4.1 km, median 18.8 km, p95 39.3 km, max 106.8 km.
Shapes average 291 points.

## Traps for anything reading this feed

- **10,497 stop_times have `arrival_time >= 24:00:00`**, up to `26:00:00`.
  Postgres `TIME` rejects those. Times are stored as integer seconds.
- **`stop_sequence` starts at 0**, not 1.
- **`stop_name` is not unique** — 2,002 names are shared by more than one stop.
  Within 500 m of Connaught Place there are two distinct stops both called
  "Shivaji Stadium Terminal", 153 m and 212 m away. Search must disambiguate
  by location.
- **38 stops fall outside a generous Delhi bounding box** (28.2–29.0 N,
  76.7–77.6 E). Not yet investigated.
- Column order in `routes.txt` is not the GTFS reference order, and
  `stop_times.txt` carries two non-standard columns (`fare_stage`, `stop_dist`).

## The fabricated timetable, quantified

OTD's own documentation says stop times are "a rough estimate generated by
assuming a constant speed of travel". Implied average speed per trip, from
route length over scheduled duration:

| p05 | median | p95 |
|---|---|---|
| 12.5 km/h | 20.7 km/h | 33.8 km/h |

So the assumed speed is *not* one global constant — it varies by route (674
distinct values at 1 d.p.). Whether it is constant *within* a trip is the
sharper question, and answering it requires the per-stop shape offsets that
`stop_dist` omits. That check is worth doing once those offsets exist: if
inter-stop time is exactly proportional to inter-stop distance, the timetable
carries no information about real traffic at all, and that is a publishable
finding about the feed rather than an opinion about it.
